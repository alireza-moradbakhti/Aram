# Aram API contract (v1)

The app is online-first: the server is the source of truth, Room is the offline
cache, and writes are queued in an outbox when the network is unavailable.
Alpha builds run against a mock implementation by default (and can be pointed at
stage); beta runs against stage; production runs against the production API.
This document is the handoff between the Android app and the backend.

- **Base URL:** `{host}/api/v1` — the host is chosen per build (see
  [Environments](#environments)); every path below is relative to `/api/v1`.
- **Transport:** HTTPS only, JSON UTF-8, `snake_case` fields.
- **IDs:** UUID v4 strings generated by the client. The server accepts them as
  opaque ids.
- **Dates:** epoch milliseconds, UTC (`Long`). Never local time, never strings.
- **Money:** integer **minor units** plus an ISO 4217 `currency_code`
  (`amount_minor: 1234`, `currency_code: "USD"` = $12.34). No floats anywhere.
- **Ownership:** `user_id` is derived from the access token. A `user_id` in a
  payload is ignored; the server must never trust it.

## Environments

Two deployments run the same contract:

| Environment | Host | Used by |
| --- | --- | --- |
| Stage | `https://test-myendpoint` *(placeholder until the backend publishes DNS)* | `alpha` with `remote` mode, `beta`, `prodDebug` |
| Production | `https://myendpoint` *(placeholder)* | `prodRelease` only |

Example: `https://test-myendpoint/api/v1/auth/login`.

- Hosts are build configuration (`aram.api.stageBaseUrl` /
  `aram.api.prodBaseUrl` in `gradle.properties`), never hardcoded in Kotlin.
- The client exposes `ApiEnvironment` (`STAGE`, `PRODUCTION`) plus an
  `EndpointProvider`; API mode (`mock` / `remote`) is a separate switch, so
  alpha can run offline-first while every remote build still knows its host.
- Contract changes are additive and must ship to stage before production.
- The production host is reachable **only** from `prodRelease`; debug builds
  never write to production data.
- Stage data is disposable and may be reset at any time. Never point a published
  build at stage, and never use production data in tests.
- A `prod` release build fails configuration if it would use the mock engine or
  a non-production host. Debug builds may override the host with
  `ARAM_API_BASE_URL`; cleartext is allowed for local servers in debug only.

## Authentication

Email + password, no third-party login in v1.

| Method | Path | Body | Returns |
| --- | --- | --- | --- |
| POST | `/auth/register` | `email`, `password`, `display_name` | `user`, `tokens` |
| POST | `/auth/login` | `email`, `password` | `user`, `tokens` |
| POST | `/auth/refresh` | `refresh_token` | `tokens` (rotated) |
| POST | `/auth/logout` | `refresh_token` | `204` |
| GET | `/me` | — | `user` |
| PATCH | `/me` | `display_name`, `default_currency`, `calendar_system` | `user` |

`tokens`:

```json
{
  "access_token": "…",
  "access_expires_at": 1763500000000,
  "refresh_token": "…",
  "refresh_expires_at": 1766100000000
}
```

- Access tokens are signed JWTs valid for **15 minutes**.
- Refresh tokens are opaque, rotated on every use, and valid for **30 days**.
  Reusing a rotated token revokes the whole family.
- Passwords are hashed with Argon2id (or bcrypt cost ≥ 12). Login errors are
  generic (`invalid_credentials`) — never reveal whether the email exists.
- Rate limit login/register by IP + email; return `429` with `Retry-After`.

## Envelope

Success:

```json
{ "data": { }, "meta": { "next_cursor": "…", "server_time": 1763500000000 } }
```

Error:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "amount_minor must be positive",
    "fields": { "amount_minor": "must be positive" },
    "request_id": "req_…"
  }
}
```

| HTTP | `code` | Client handling |
| --- | --- | --- |
| 400 / 422 | `validation_failed` | Show field errors; do not retry |
| 401 | `unauthorized` / `token_expired` | Refresh once, then sign out |
| 403 | `forbidden` | Show permission error; do not retry blindly |
| 404 | `not_found` | Remove the local row or refresh |
| 409 | `conflict` | Reconcile with the returned canonical row |
| 429 | `rate_limited` | Honor `Retry-After`, back off |
| 5xx | `server_error` | Retry with exponential backoff, then queue |

Every response carries `X-Request-Id`; log it in the app (never with amounts or
names) so a device report can be matched to server traces.

## Resources

All list endpoints accept `limit` (default 100, max 200), `cursor`, and
`updated_since` (epoch millis). Lists return `data: [...]` and
`meta.next_cursor`.

### `user`

```json
{
  "id": "…",
  "email": "…",
  "display_name": "…",
  "default_currency": "USD",
  "calendar_system": "GREGORIAN",
  "created_at": 0,
  "updated_at": 0
}
```

### `account`

`id`, `name`, `type` (`CASH|BANK|WALLET|SAVINGS|INVESTMENT`),
`currency_code`, `opening_balance_minor`, `color_argb`, `icon_key`,
`sort_order`, `archived`, `created_at`, `updated_at`, `deleted_at`.

### `category`

`id`, `name`, `kind` (`INCOME|EXPENSE`), `parent_id`, `color_argb`,
`icon_key`, `archived`, timestamps.

### `transaction`

`id`, `account_id`, `category_id` (null for transfers), `type`
(`INCOME|EXPENSE|TRANSFER`), `amount_minor` (always positive), `currency_code`,
`occurred_at`, `note`, `transfer_group_id`, `recurring_rule_id`, timestamps.

A transfer is one logical operation with two rows sharing
`transfer_group_id`. The server must accept both rows in a single batch so the
transfer is atomic.

### `budget`

`id`, `category_id`, `period_start_epoch_day`, `limit_minor`, `currency_code`,
timestamps. Unique per `(user_id, category_id, period_start_epoch_day)`.

### `goal` / `goal_contribution`

Goal: `id`, `name`, `target_minor`, `currency_code`, `deadline_epoch_day`,
`status` (`ACTIVE|COMPLETED|ARCHIVED`), timestamps.
Contribution: `id`, `goal_id`, `amount_minor`, `occurred_at`, timestamps.

### CRUD

| Method | Path |
| --- | --- |
| GET / POST | `/accounts`, `/categories`, `/transactions`, `/budgets`, `/goals` |
| PATCH / DELETE | `/accounts/{id}`, `/categories/{id}`, `/transactions/{id}`, `/budgets/{id}`, `/goals/{id}` |
| POST / DELETE | `/goals/{id}/contributions`, `/goals/{id}/contributions/{contribution_id}` |

- `DELETE` is a **soft delete**: the server sets `deleted_at` and `updated_at`
  and keeps the row as a tombstone.
- Writes must carry `Idempotency-Key: <uuid>`; the server stores the key for at
  least 24 hours and replays the original response on retry.
- Writes are **last-write-wins per row** on `updated_at`. If the incoming
  `updated_at` is older than the stored row, return `409 conflict` with the
  canonical row in `error.details.current`.
- Client timestamps are trusted only for ordering, never for authorization.

## Sync

Pull:

```
GET /sync?since=<server_time_ms>&cursor=<opaque>
```

```json
{
  "data": {
    "changes": {
      "accounts": [ { } ],
      "categories": [ { } ],
      "transactions": [ { } ],
      "budgets": [ { } ],
      "goals": [ { } ],
      "goal_contributions": [ { } ]
    }
  },
  "meta": { "next_since": 1763500000123, "next_cursor": "…", "has_more": false }
}
```

- `server_time`/`next_since` is a **monotonic server revision** (a per-user
  sequence or `server_updated_at`), not the client clock.
- Deleted rows appear with `deleted_at` set. The client applies tombstones and
  filters them from reads.
- Page until `has_more` is false; persist `next_since` only after a full pull
  completes.

Push:

```
POST /sync/push
```

```json
{
  "mutations": [
    {
      "idempotency_key": "uuid",
      "entity": "transaction",
      "op": "upsert",
      "id": "uuid",
      "client_updated_at": 1763500000000,
      "payload": { }
    }
  ]
}
```

```json
{
  "data": {
    "results": [
      { "idempotency_key": "uuid", "status": "applied", "row": { } },
      { "idempotency_key": "uuid", "status": "conflict", "row": { } },
      { "idempotency_key": "uuid", "status": "rejected", "error": { } }
    ]
  },
  "meta": { "server_time": 1763500000123 }
}
```

Rules:

1. Mutations are applied **in array order**; a transfer's two rows appear
   together in one request.
2. `applied` includes the canonical row, including server-assigned
   `updated_at` if the server adjusts it.
3. `conflict` returns the winning row; the client overwrites its local copy and
   clears the outbox entry.
4. `rejected` is permanent (validation/authorization); the client marks the
   local row `FAILED` and surfaces it rather than retrying forever.
5. Partial success is allowed. Clients retry only non-applied mutations.

## Alpha mock

Until stage is deployed, alpha builds use a Ktor `MockEngine` that implements
every route above with in-memory fixtures and realistic latency (300–800 ms).
The same build can switch to the stage host with `ARAM_API_MODE=remote` once the
backend is live. The mock must:

- seed a demo user, two accounts, categories, and ~30 transactions,
- return the same envelopes and error codes as the contract,
- support toggling offline/failure scenarios from a debug menu,
- be swappable for the real remote source through one Hilt binding
  (`ARAM_API_MODE=mock|remote`), with no feature-module changes.

Contract tests run every DTO against the fixture JSON in this document; a
backend change that breaks the shape fails CI.

## Non-goals for v1

- WebSockets or push notifications (poll / pull-to-refresh first).
- Multi-device real-time merge beyond last-write-wins.
- Shared budgets or households (schema keeps `user_id`, but no sharing API).
- Bank aggregators and multi-currency conversion.
